# Steam-рулетка: как я сделал колесо, которое выбирает, во что играть

*Теги: steam, javascript, react, supabase, pet-project, web-разработка*

У каждого геймера есть бэклог: сотня купленных на распродажах игр и вечный вечерний ритуал — 20 минут листать библиотеку и в итоге запустить то же, что и вчера. Я задолбался и сделал инструмент, который решает за меня: колесо фортуны по списку игр, с живыми ценами Steam на секторах и шарингом одной ссылкой.

Живое демо: https://dvinerlove.github.io/fortune-wheel/
Код (MIT): https://github.com/dvinerlove/fortune-wheel

В статье — как устроено приложение, и три нетривиальных места: честный рандом с анимацией, шаринг состояния без аккаунтов, и защита публичного API от спама.

## Что умеет

- Крутит колесо по вашему списку игр; у каждой игры равный сектор и шанс 1/N
- Автоматически находит игру в Steam: живые цены, скидки и обложки прямо на колесе
- Шаринг колеса короткой ссылкой — друг получает ваш список и все настройки
- Пресеты списков («бэклог», «на компанию»), скрытие игр из розыгрыша, режим выбывания победителя
- RU/EN интерфейс, синтезированные звуки через Web Audio API, кастомные фоны и цвета
- Без регистрации: данные в localStorage, ничего не уходит на сервер (кроме анонимного счётчика визитов)

## Стек

React 19 + TypeScript + Vite + Tailwind на фронте, GitHub Pages для хостинга. Бэкенд — одна Supabase Edge Function (Deno) + Postgres для шаров, кэша цен и маппингов имён игр → appId.

## 1. Честный рандом с анимацией

Типичная ошибка в таких колёсах — сначала анимируют «куда придёт», потом подгоняют результат. Я сделал честнее: `crypto.getRandomValues` сразу определяет целевой угол, колесо крутится `1440° + random * 2160` с easing'ом `easeOutExpo`, а индекс победителя вычисляется из конечного угла под указателем. Анимация — чистая визуализация уже выбранного исхода.

Приятная деталь — звук. Тики синтезируются осциллятором на каждом пересечении границы сектора, с двумя нюансами, без которых звучит как каша:

- **Троттлинг 40 мс**: на пике скорости колесо пролетает 2–3 границы за кадр, и каждая запускала осциллятор — получался треск
- **Огибающая громкости**: fade-in в первые 8% спина и спад `1 - progress^1.4` к концу — колесо «затихает» вместе с замедлением

## 2. Шаринг без аккаунтов

Хотелось «поделиться колесом» одной ссылкой. Состояние — список игр + все настройки темы — сериализуется в JSON. Дальше два уровня:

1. **Короткая ссылка** `?share=abc123`: edge function хэширует payload (SHA-256), отдаёт существующий шар при совпадении — идемпотентно, база не дублирует одинаковые колёса
2. **Длинная ссылка** `?state=base64` — фоллбэк, если API недоступен: всё состояние в самом URL, сервер не нужен

Плюс localStorage как третий уровень — обычное использование вообще не требует сети. Результат: шаринг работает даже с мёртвым бэкендом, просто ссылка некрасивая.

## 3. Спам на публичном API

Edge function публичная — POST эндпоинты шаров и маппингов без авторизации (в этом и смысл). Классическая дилемма: либо спамить можно сколько угодно, либо вводить авторизацию и убить UX.

Компромисс — per-IP rate limit через таблицу `rate_limits` (ключ = `bucket:ip`, счётчик + `window_start`):

- шары: 30/час, маппинги: 60/мин, трекинг: 60/мин
- отсутствие таблицы → fail-open с логом, деплой не ломается
- тело шара > 5MB → 413 (юзерские картинки — base64, их и лимитируем)

Плюс ленивая уборка: ~2% write-запросов удаляют строки `rate_limits` старше суток — cron не нужен, таблица не разрастается.

## 4. Мелочи, которые оказались важны

- **Не блокировать первый рендер на сети**: изначально игры не рисовались, пока не ответят ~80 параллельных запросов автоматпинга Steam. Chromium кидал `ERR_INSUFFICIENT_RESOURCES`, а пользователь видел пустое колесо. Теперь список рендерится мгновенно, маппинг догоняет батчами по 4
- **Per-key парсинг localStorage**: один битый JSON-ключ не должен убивать остальные данные
- **Демо-игры при первом визите**: пустое колесо — плохое первое впечатление, поэтому подсев 8 популярных тайтлов, пока ключ не существует в storage
